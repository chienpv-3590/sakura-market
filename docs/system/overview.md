## Executive Summary

Sakura Market (産地市場) is a Japanese fisheries **wholesale-market operations system**. It implements one continuous business chain: lot intake (荷受) → quality assessment (目利き) → sale by either negotiated trade (相対取引) or auction (せり) → delivery → daily reconciliation → an irreversible business-day lock → post-lock correction under maker-checker → incentive calculation (完納奨励金) → accounting data export (`README.md:3-9`; `docs/pham-vi-va-phan-mock.md:16-39`). The UI is bilingual (Vietnamese / Japanese, `src/lib/i18n/config.ts:1-23`), and seven roles (買出人-adjacent internal roles, not customer-facing) — ROLE-INTAKE, ROLE-JUDGE, ROLE-TRADE, ROLE-DELIVERY, ROLE-SETTLEMENT, ROLE-RULE-ADMIN, ROLE-SYS-ADMIN — each land on a role-specific screen after sign-in (`src/lib/auth/role-landing.ts:3-32`).

The codebase is an explicitly-labelled **prototype** ("LAB-3"), built to a stated ~11-hour budget, running against seed/mock data only — not a production deployment (`README.md:1-9`). Of 32 originally-scoped screens, 20 are built across 11 features (F001–F011); the remaining 12 are declared out of scope with a stated reason each (MFA and account-management screens deferred on purpose; a few P1 report/notification screens deferred for budget; two reports — delivery-exception and dispute — structurally unbuildable because no write path or table exists for the states they'd report on) (`docs/pham-vi-va-phan-mock.md:16-62,73-85`). There is **no automated test suite** — a recorded, deliberate waiver, not an oversight; correctness for the Postgres-tier guarantees (lock trigger, CAS-based oversell prevention) was instead demonstrated with live scripts against a running database (`docs/pham-vi-va-phan-mock.md:138-147`). The app has no background/scheduled logic: the scout inventory found exactly two markers, both plain DOM `addEventListener` calls in a UI component, no cron/queue/scheduler (`src/components/layout/nav-shell.tsx:29,32`; `scout-report.md:327-333`). The detected API surface is REST, served entirely through PostgREST/Supabase's auto-generated endpoints plus Next.js Route Handlers under `src/app/api/**` (`scout-report.md:334`).

For architecture diagrams and full tech-stack detail, see [architecture.md](architecture.md).

## Key Design Decisions

### Decision 1: No cross-table database transactions — compare-and-swap plus compensating writes

**Context**: PostgREST (the API layer Supabase Postgres is reached through) does not grant a client `BEGIN`/`COMMIT` across multiple statements — there is no way for application code to wrap two related writes in one real Postgres transaction (`docs/pham-vi-va-phan-mock.md:152-159`).

**Decision**: Every multi-step business write (approve a correction, approve an incentive rule version, create an accounting export batch) is expressed as a status-column compare-and-swap (`UPDATE ... WHERE status = 'pending'`) that also serves as the concurrency guard, optionally followed by a dependent insert; if the dependent insert fails, the code explicitly compensates by writing the CAS status back to its prior value rather than leaving an inconsistent row standing (`src/lib/corrections/approve-correction.ts:38-156`, compensation at `:133-143`; same idiom in `src/lib/incentive/approve-rule-version.ts:17-57`).

**Rationale**: A real crash between two writes (e.g. after decrementing available quantity but before inserting the transaction row) can still leave state briefly inconsistent and require manual cleanup — an accepted, explicitly documented trade-off for the prototype; a production build would need this logic moved into a PL/pgSQL function running inside one real Postgres transaction (`docs/pham-vi-va-phan-mock.md:152-159`).

### Decision 2: Irreversible business-day lock, enforced by a Postgres trigger against every caller including `service_role`

**Context**: Once a business day is reconciled and locked, four operational tables (`transaction`, `seri_result`, `mekiki_record`, `delivery_shipment`) must never be written to for that date again — by any caller, including server-side admin code (`docs/pham-vi-va-phan-mock.md:130-131`).

**Decision**: `lockBusinessDay()` inserts one row into `business_day_lock`; the table's own primary key (`business_date`) is the actual serialization point — a second concurrent lock attempt hits Postgres error `23505` and is translated to `ALREADY_LOCKED` (`src/lib/reconciliation/lock-business-day.ts:9-46`). Enforcement itself lives entirely in a `BEFORE UPDATE/DELETE` trigger, `trg_block_after_lock`, which raises SQLSTATE `P0001` (`supabase/migrations/20260904090500_business_day_lock.sql:22-73`); the app layer only translates that error into HTTP 423 and writes an audit row (`src/lib/reconciliation/handle-locked-write.ts:6-42`). There is deliberately no unlock path anywhere in the codebase, for any role (`src/lib/reconciliation/lock-business-day.ts:14-16`).

**Rationale**: An earlier version tried to enforce the lock via RLS policy conditions instead of a trigger, and that approach was empirically found broken twice — once because `service_role` lacked schema privileges to even reach the lock-check function (returned a permission error instead of the lock error), once because RLS's row-filtering happens *before* the trigger runs, so a normal client saw a silent empty result instead of the intended lock error. The fix moves the lock check out of RLS entirely and into the trigger, so every caller — authenticated, `service_role`, or a raw `psql` session — hits the same `P0001` (`supabase/migrations/20260904091100_lock_enforcement_fix.sql:1-22`). This is a documented, evidence-driven decision, not a theoretical one.

### Decision 3: Two-tier authorization — session existence at the edge, role/active-status deeper, both fail closed

**Context**: Every business route needs both "is there a session" and "is this specific role allowed here," and page-level authorization must not leak the existence of resources a role cannot see.

**Decision**: Tầng 1 (`proxy.ts`, Next.js 16's renamed middleware convention — see `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md:11`) runs on almost every request, refreshes the Supabase session cookie, and redirects to `/login` only when no session claims exist at all (`src/proxy.ts:1-12`; `src/lib/supabase/proxy.ts:11-59`). Tầng 2 (`requireUser()`/`requireRole()`, called at the top of Server Components and Route Handlers) additionally requires the signed-in `app_user` row to be `is_active` and, for role-gated routes, requires the role to be in an allow-list — an unauthorized role gets a `404`, not a `403`, so it gets no signal a resource even exists (`src/lib/auth/require-role.ts:57-78`). A lookup ambiguity (an inactive account's own row read comes back empty exactly like "row doesn't exist," because `read_all_active_users` RLS requires the caller's own row to already be active) is resolved by treating both cases as "no session" rather than guessing (`src/lib/auth/require-role.ts:15-27`).

**Rationale**: Two independent gates mean a bug in one (e.g. a missing `requireRole()` call on one route) is still caught by the other's RLS write policies at the database level — confirmed for writes in `README.md:79-81` ("Thử qua API cũng bị Postgres chặn, không chỉ ẩn nút trên giao diện").

### Decision 4: Full-table read for every active role; write is role-scoped by RLS

**Context**: RFP requirement `FR-601` requires other roles to see the full picture for shared business tables at read time, even though they cannot act on it.

**Decision**: RLS is enabled on the business tables; a single shared policy, `read_all_active_users`, grants `SELECT` to every authenticated row across all of them — `app_user`, `audit_log`, `participant`, `lot`, `transaction`, `seri_result`, `delivery`, `business_day_lock`, `correction_request`, `incentive_rule_version`, `incentive_result`, `payment_record`, etc. (`supabase/migrations/20260904090900_rls_core.sql:28-61`). Write access is then narrowed per table by role-scoped policies (e.g. `write_intake` on `lot`, `write_judge` on `mekiki_record`) (`supabase/migrations/20260904090900_rls_core.sql:71-96`). README's "16 business tables" figure (`README.md:73`) excludes the two identity/audit tables (`app_user`, `audit_log`) from that count; the migration's 18 `public` tables include those two plus the 16 (`supabase/migrations/*.sql`, verified by direct grep of `create table` statements).

**Rationale**: Deliberate transparency across roles at read time (a judge can see the full trade screen exactly as a trader would, `README.md:76-78`) traded for strict role isolation only where it actually matters — the write path.

### Decision 5: The incentive (完納奨励金) engine runs synchronously inside the request, not as a background job

**Context**: The functional spec describes incentive recalculation as background-job-triggered work, but this stack has no queue infrastructure within its budget.

**Decision**: `runIncentiveForPeriod()` is invoked directly, in-process, right after a business day is locked or a correction is approved (`runIncentiveDeltaAfterApproval` in the corrections-approve route) — not dispatched to any worker (`src/lib/incentive/run-incentive-for-period.ts:13-31`; `docs/pham-vi-va-phan-mock.md:148-151`). The caller must swallow any error the engine itself throws, so a failure in incentive calculation never blocks the primary action (locking the day) from succeeding (`src/lib/incentive/run-incentive-for-period.ts:18-20`).

**Rationale**: Recorded as an intentional, budget-driven deviation from the original design, not an oversight — flagged for a follow-up ADR (`src/lib/incentive/run-incentive-for-period.ts:14-16`).

## Security Overview

- **Authentication**: Supabase Auth (GoTrue) reached via `@supabase/ssr`; the session cookie is refreshed on nearly every request by `proxy.ts` → `updateSession()` (`src/lib/supabase/proxy.ts:11-59`). Sign-in failures are rate-limited: 5 consecutive failed attempts locks the account for 15 minutes, tracked in `app_user.failed_login_count`/`locked_until` via the admin (service-role) client since no session exists yet at that point (`src/lib/auth/lockout.ts:10-42`). MFA is available in the underlying Supabase Auth product but is **deliberately not enabled** — enabling it is incompatible with the 9 demo accounts sharing one password, and is recorded as deferred until before a real production rollout (`docs/pham-vi-va-phan-mock.md:75`). Session inactivity timeout is present in config but commented out (`supabase/config.toml:271,275`) — also a recorded, not accidental, gap (`docs/pham-vi-va-phan-mock.md:77`).
- **Authorization**: Role-based access control over 7 fixed roles (`src/lib/auth/role-landing.ts:3-20`), enforced at two independent layers — see Decision 3 above. Role values arriving from the database are validated against the known set before use; an unrecognized value fails closed rather than falling through to a default role (`src/lib/auth/role-landing.ts:38-46`).
- **Data Encryption**: Not directly evidenced in application code — transport security and at-rest encryption are inherited from the managed Supabase/Vercel hosting, not configured by this codebase `[UNVERIFIED]`.
- **API Security**: The Supabase secret key is confined to a single file, guarded at build time by the `server-only` package import, so any Client Component importing it fails the build (`src/lib/supabase/admin.ts:1-21`). The browser client uses only the publishable (public) key (`src/lib/supabase/client.ts:1-10`). Every server-side Supabase client is created fresh per request rather than held globally, matching the stateless/Fluid-compute execution model (`src/lib/supabase/server.ts:5-6`). The business-day-lock trigger is the one place enforcement is pushed to the database layer itself so that it holds even against the service-role client (Decision 2).

## Scalability

- **Current Capacity**: No capacity target is documented anywhere in the repository — this is a demo-scale prototype running on seed data, not a load-tested system `[UNVERIFIED — absent, not merely unread]`. The project runs on Supabase's free tier, which auto-pauses after 7 days without a query and takes ~30 seconds to resume (`README.md:89-95`).
- **Scaling Strategy**: None is implemented or documented. The Next.js app itself is stateless (no server-held session; a fresh Supabase client per request, `src/lib/supabase/server.ts:5-6`) and is horizontally scalable in principle on a platform like Vercel (`README.md:97-99`). The realistic bottleneck under concurrent load is Postgres-side: sequence-number races on `accounting_export_batch` are retried up to 5 times before giving up (`src/lib/accounting/create-export-batch.ts:9,48-90`), and the synchronous incentive engine (Decision 5) runs inline in the lock/approve request path with no queue to absorb load.
- **Performance Targets**: None found — no NFR-PERF or equivalent requirement exists in the repository's docs `[UNVERIFIED — absent]`.
